# Data layer

TypeScript owns SQLite, alone (PASSPORT decision D2). Rust never opens the database: it returns
results across the boundary and the host persists them through a repository. One writer, one
schema owner, one migration tool.

## Layout

| File            | Role                                                                                                                                                         |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `client.ts`     | Opens `better-sqlite3`, sets the pragmas, exposes the Drizzle connection and `transaction`. Created by the composition root, never a module-level singleton. |
| `types.ts`      | `Database`, `Transaction`, `DatabaseHandle` — what a repository is handed.                                                                                   |
| `UnitOfWork.ts` | The port services depend on, so `services/ → repositories/` stays the only arrow into persistence.                                                           |
| `schema/`       | One file per table plus a barrel. Table names snake_case, TS camelCase.                                                                                      |
| `migrations/`   | Generated by `drizzle-kit`, committed. Migrations are source, not artefacts.                                                                                 |
| `migrate.ts`    | Backs up, applies pending migrations, throws `MigrationFailedError`.                                                                                         |
| `repositories/` | The only code that touches Drizzle queries.                                                                                                                  |

## Rules for repositories

1. **Intention-revealing methods only.** `findEnabledByCapability`, never a leaked query builder
   and never a raw `where` passthrough. The query stays inside the repository so the set of ways
   a table can be read stays finite and reviewable.
2. **Repositories return entities** — row shapes straight from the schema. Mapping an entity to a
   DTO happens in a service, because the two shapes are allowed to diverge.
3. **Repositories never open a transaction.** A service calls `UnitOfWork.transaction(fn)`; every
   repository handed to `fn` shares that unit of work, so one operation can span several
   aggregates. `fn` throwing rolls the whole unit back.

`SettingRepository` is the template every later repository copies.

## Migrations

`pnpm --filter studio db:generate --name=<change>` writes a new SQL file and updates the journal.
Commit both. `migrate()` runs in the composition root **before any service is constructed**: it
copies the database to `userData/backups/db-<timestamp>.sqlite` (keeping the last three, skipped
when the database has no tables yet), applies what is pending, and logs each migration by tag. A
failure throws `MigrationFailedError`, and the composition root opens a recovery window instead of
the app — the app never runs against a half-migrated schema.

`electron.vite.config.ts` copies `migrations/` next to the built host entry, so the runner finds
the same folder in development, in a build, and inside a packaged asar.

## Native module

`better-sqlite3` must match Electron's Node ABI, not the system Node's. `postinstall` runs
`electron-rebuild -f -w better-sqlite3`. Because of that, the test suite runs under the Electron
binary in pure-Node mode (`scripts/run-tests.mjs`), not under the system Node.
